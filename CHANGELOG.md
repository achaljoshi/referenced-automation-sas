# Changelog

## Unreleased

> **NOT VERIFIED.** Everything below was developed and tested on macOS against stand-ins (a fake desktop with a fake Management Console, a fake Enterprise Guide and a fake Enterprise Guide COM object model, and a stand-in bridge program speaking the real line protocol). Nothing has run on a real Windows desktop with the real SAS programs; what only a real machine can prove is labelled NOT VERIFIED where it is described, and `npm run doctor` / `npm run test:conformance` are the first checks to run there.

### Added
- **Sample tests for a machine with SAS** (`features/real/sample_01_command_line.feature`, `sample_02_management_console.feature`, `sample_03_enterprise_guide.feature`; `npm run test:real-samples`): read-only. They take what to look at from `SAS_SAMPLE_TOOL`, `SAS_SAMPLE_TOOL_ARGS`, `SAS_SAMPLE_TOOL_EXPECT`, `SAS_SAMPLE_TOOL_EXIT`, `SAS_SAMPLE_SMC_USER`, `SAS_SAMPLE_EG_PROJECT` (`.env.example` section 12). Opt-in like the other real-program tests; the pipeline runs them on the stand-in, and `sas-desktop-samples` is the manual Windows job. NOT VERIFIED on a real installation.
- **`sasTest`** (the command-line route): `sasProcess` (the `ProcessDriver` on the safety policy), `sasTools` (a `BatchToolRunner` per table of `SAS_BATCH_TOOLS_FILE`), and the settings, environment, run context and policy. It has no desktop gate, so it runs on Windows, macOS and Linux. `desktopTest` extends it.
- **README restructured like the other repos**: a route chooser, Quick start, Windows first run, the sample tests, **Using it from the command line**, **Using it for the desktop**, What's included, Gherkin / BDD, CI/CD, First rollout, Testing this package itself. `docs/WINDOWS_FIRST_RUN.md` and `examples/README.md` follow.
- **Operating systems** (`docs/PLATFORMS.md`): what runs on Windows, macOS and Linux and what needs Windows. `npm run doctor` prints it for the machine (`describePlatform`, `src/desktop/platform.ts`) and on a system that cannot reach a Windows desktop reports that and exits 0 instead of failing. One rule (`reachesRealDesktop` / `reachesDesktop`) now decides whether a desktop can be reached; the test gate, the worker plan and `doctor` all use it. `.gitattributes` stores every text file with LF so a Windows checkout does not change generated files and examples. `tests/portability.spec.ts` enforces the portability rules on `src/` (no shell, no `exec`, no `/tmp`, no Unix commands by name). Windows is NOT VERIFIED: the suite has not been run there; the manual `test-windows` job runs it.
- **The tests of the real programs are opt-in** (`tests/real`, `features/real`): they log on to the real Management Console and Enterprise Guide, so they are skipped with the reason unless asked for. `npm run test:conformance` and `npm run test:real-smoke` ask (`scripts/run-real.js` sets `SAS_REAL_TESTS=true`, the same on every shell); `SAS_DESKTOP_SIMULATOR=true` runs them against the stand-in as before. Before this, a plain `npm test` on a Windows machine with SAS would have opened the programs and typed a login. New settings `SAS_REAL_TESTS` and `SAS_TEST_NODE_LAUNCH` are in `.env.example`.
- `DesktopApp.dispose()` also stops a launched program that has no window left (for example after a cancelled logon); the stand-in shows the old behaviour left it running.
- **Scope**: this repo automates the SAS **desktop** programs (SAS Management Console, SAS Enterprise Guide). **SAS Viya is out of scope**; the family's `api` and `ui` packages cover it. The order of preference is command line > COM > screens (ADR 0001, `docs/AUTOMATION_APPROACHES.md`).
- **Fixtures** (`src/fixtures`): `desktopTest` and `desktopExpect`. Per worker: `desktopSession` (the bridge hash is verified, the transport is chosen by `SAS_DESKTOP_TRANSPORT`, the stand-in desktop with `SAS_DESKTOP_SIMULATOR=true`), `environment`, `runContext`, `safetyPolicy`, `desktopGuard`, `fakeDesktop`. Per test: `smcApp`, `egApp` (launched or attached, not logged on), `smcLoggedOn`, `egLoggedOn` (logged on through the core `LogonGuard.protect`; a rejected logon is typed once and Playwright's retries are stopped by the guard's cooldown), `smc`, `eg`, `egCom`, `cleanup`, `vars` (with `{{runId}}` and `{{namespace}}`).
- **The policy adapter** (`src/fixtures/guardAdapter.ts`): plugs the core `SafetyPolicy` and `AuditLog` into the desktop layer's `OperationGuard` - supplies the environment, forwards results, treats steps with no host as local, exempts raw UI steps from the namespace rules only (production still refuses them), and judges closing a program the run started as a read (`housekeeping`). `tests/fixtures/guardAdapter.spec.ts` proves each rule against the real policy and the real desktop layer.
- **Pre-flight health gate** (`SAS_PREFLIGHT`, default on): once per worker, the core checks (environment declared, state folder and audit log writable), a logon-cooldown check per configured login, and the desktop session's (bridge answers, interactive, unlocked, UI Automation). One failure listing every red check with what to do.
- **Evidence** (`SAS_EVIDENCE`: `off`, `failure` (default), `on`, `steps`): a screenshot and the step journal (masked) for a failed test; under the run's own folder, other runs' folders pruned after `SAS_EVIDENCE_RETENTION_DAYS`; the bridge paints password fields black.
- **Clean-up** after the test, pass or fail, while the program is still open; a failed clean-up fails the test unless `SAS_CLEANUP_FAILURE=warn`.
- **One desktop, one worker**: `playwright.config.ts` sets one worker where a real desktop can be reached; the `desktopHost` fixture refuses more. `initRunContext()` gives every worker the run's id.
- **Gherkin** (`src/bdd`, `features/`): `registerDesktopSteps` with a business-readable vocabulary (`Given SAS Management Console is open and I am logged on`, `When I open the "User Manager" plug-in`, `Then the user "..." is listed`, `When I open the Enterprise Guide project "..."`, `And I run the project`, `Then the program "..." finished without errors`, `Then the window title contains ...`, generic click / enter / select / remember steps, `I enter the secret "SAS_PASSWORD" ...` that never echoes a value); `SAS_ASSERT_TIMEOUT_MS` for the assertion steps. The step texts are a public contract (`tests/bdd/vocabulary.spec.ts`). Four sample features (`@smc-ui`, `@eg-com`, `@eg-ui`, `@smoke`, `@regression`, `@sas-desktop`) run on the stand-in as the `bdd` project.
- **Worked examples** (`features/example_*.feature`, `examples/README.md`): Management Console, Enterprise Guide by COM, Enterprise Guide screens, and the safety policy, each line explained with the `.env` key it uses; `npm run try:simulator` runs them and prints what each does.
- **Checks for a real machine** (`tests/real/conformance.spec.ts`, `features/real/smoke.feature`): `npm run test:conformance` (no login, changes nothing) and `npm run test:real-smoke` (read-only). Skipped with the reason anywhere a desktop cannot be reached; `SAS_DESKTOP_SIMULATOR=true` runs them on the stand-in.
- **Configuration**: `.env.example` is the one exhaustive, authoritative reference (first things to fill in, environments and safety, credentials, Management Console, Enterprise Guide, command-line tools, transport, evidence and timing, test data and clean-up, recorder, simulator and CI), each variable with purpose, valid values, default, required, secret and where to find it; `.env.local.example` is the secrets template (`.env.<ENV>.local`); `env/sas-environments.json` (declares `simulator`) and `env/sas-environments.json.example`; `.env.dev` / `.env.qa` / `.env.stage` hold only non-secret placeholders; `.env.simulator`. `tests/envDocs.spec.ts` fails when a variable the code reads is missing from `.env.example` or the README's "Configuration reference" table, or one they list is read by nothing. The `env/core.example` and `env/desktop.example` fragments were merged into `.env.example` and removed; the recorder's `env/recorder.example` is merged too (its variables are in section 10), and `tests/envDocs.spec.ts` fails if it lists one that `.env.example` does not.
- **Documentation**: `README.md` (what the repo is and is not for, the order of preference, quick start, fixtures, tags, Gherkin, configuration reference, safety rules, Windows first run in PowerShell, troubleshooting table, what is and is not verified), `docs/ARCHITECTURE.md`, `docs/WINDOWS_FIRST_RUN.md`, `docs/adr/README.md`, `CONTRIBUTING.md`.
- **Pipeline** (`.gitlab-ci.yml`): `build` (typecheck, lint, bridge-hash check), `test` (the whole suite against the stand-in on the Linux image with the minimum-executed gate), `security` (non-blocking until its first green run), `audit` (manual), `pages`; and two manual Windows-runner templates, `sas-desktop-conformance` and `sas-desktop-smoke` (placeholder runner tag, `allow_failure: true`, NOT VERIFIED).
- **Core** (`src/core`): environments allow-list, safety policy (every rule in `docs/SECURITY.md`), credentials, logon guard, audit log, run context, health gate, clean-up registry. **Process driver** (`src/process`). **Desktop layer** (`src/desktop`): the PowerShell bridge with a pinned SHA-256, UI Automation locators and assertions, COM client, `SasEnterpriseGuide`, `SasManagementConsole`, `SasEnterpriseGuideUi`, the stand-in desktop and stand-in bridge, `sas-desktop-inspect` (`npm run doctor`, `npm run inspect -- --app smc`). See `docs/SECURITY.md` and `docs/DESKTOP_SAS.md`.
- **Recorder** (ADR 0002): see `docs/RECORD_AND_PLAY.md` and section 10 of `.env.example`.

### Changed
- **The plain specs that tested behaviour are Gherkin scenarios now** (playwright-bdd; `npm test` runs `bddgen && playwright test` as before). The four worked examples (`tests/examples`) are `features/example_*.feature`, tagged `@example`; `npm run try:simulator` generates and runs them. The three samples and the smoke checks of the real programs (`tests/real/sample_*.spec.ts`, `smoke.spec.ts`) are `features/real/*.feature`; `scripts/run-real.js` generates them and runs the `bdd-real` project for `@real-sample` and `@real-smoke` (`@real-conformance` is still the plain `tests/real/conformance.spec.ts`), and the opt-in (`tests/support/realOptIn.ts`) is applied to every scenario of that folder by an automatic fixture of its own `test`. The production-is-read-only checks (`tests/fixtures/production.spec.ts`) are `features/production/production.feature`, the `bdd-production` project. Every check of the old specs is a step of the scenarios; the steps this repo adds for them (`features/support/sasSteps.ts`, `realSteps.ts`) are its own, not part of the shipped vocabulary (`src/bdd` is unchanged). Plain specs remain for the framework itself: unit tests of the library, documentation, environment and portability guards, the fixtures, the vocabulary, the recorder and the conformance check (README, "Gherkin / BDD"). `tests/bdd/vocabulary.spec.ts`, `tests/scripts.spec.ts`, `tests/optInForRealTests.spec.ts` and `tests/envDocs.spec.ts` follow the move. The `--min` of `test:bdd` is 23 (the `bdd` and `bdd-production` scenarios; the `bdd-real` ones are opt-in); `test:smoke` and `test:regression` still select the same scenarios.
- The Windows first-run documents run the real-program tests through `npm run test:conformance` / `test:real-samples` / `test:real-smoke` (they are opt-in now); `tests/envDocs.spec.ts` no longer assumes the order of the README's sections.
- `npm run inspect` now runs the `inspect` command (`npm run inspect -- --app smc`); it used to be the bare tool, which printed its usage for that line.
- New npm scripts `inspect:windows` and `bridge:path` (the bare `npm run inspect -- windows` / `-- --print-bridge` cannot work through the `inspect` script); `test:ci`, `test:bdd`, `test:smoke`, `test:regression`, `test:conformance`, `test:real-smoke`, `try:simulator`.
- `package.json` description no longer claims SAS Viya support.

- The host allow-list cannot be enforced for the desktop programs: they connect through their own saved profiles, so their steps are `local`. The environment kind, the namespace rule and the audit log are enforced.
- The app fixtures launch and log on once per **test**, not once per worker (a test that wants the logon dialog needs a program that is not logged on); `docs/SECURITY.md` asks for one logon per worker.
- `SAS_EVIDENCE=steps` is accepted by the fixtures; the core's `RunContext.evidenceMode` itself only knows `off`, `failure`, `on` (the fixtures translate).
